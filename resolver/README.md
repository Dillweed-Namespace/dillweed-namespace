# DillClaw Resolver — v0.1.8

Reference implementation of the [DillClaw Resolver Specification v0.1](https://dillweed.com/dillclaw-spec.html).

The DillClaw Resolver is the operational layer for the [Dillweed Namespace](https://dillweed.com/namespace-standard.html). It takes a namespace URI — either the canonical short form `dllwd://` or the full form `dillweed://`, which the resolver treats as equivalent per Namespace Standard §3.4 — applies trust policy, selects the best available capability, and returns an invocable endpoint.

**Zero external dependencies.** Requires only Node.js 14+.

---

## ⚠ Important: Trust Roots and Public Keys

The DillClaw Resolver verifies Capability Record signatures against a configured DNSO public key. The key it uses determines what trust root the resolver is operating under.

What this means:

- If you configure the resolver to verify against a development public key (your own, or one generated by a local Registry instance), the resolver is operating against **a local trust root**. Records it accepts as valid are valid only within that local trust context.
- To verify against the **canonical Dillweed Namespace**, configure the resolver to use the DNSO public key published at `https://dillweed.com/dnso_public.pem`.
- Operating a public-facing instance of this resolver against a local development key would **not** constitute "running the Dillweed Namespace resolver." It would be a separate resolver that uses DillClaw's code and protocols but is bound to a different trust root.
- The Dillweed® mark is registered in the United States; DillClaw™ and Dillweed Anthill™ are common-law trademarks. The marks are protected. Publishing services or running infrastructure under the "Dillweed Namespace" name without DNSO authorization is not permitted.

See the [implementation guide §08](https://dillweed.com/implementing-dillweed.html#key-handling) for the full trust-root model.

## What's new in v0.1.7

- **Pass 2 conformance audit fixes** — eight defects against the DillClaw Resolver Specification v0.1.3 corrected. All eight changes are implementation-side; no spec amendments were required.
- **RFC 3339 timestamp conformance** — `resolved_at`, `cached_at`, and the `/health` `timestamp` now use second-precision UTC (`YYYY-MM-DDTHH:MM:SSZ`). Earlier releases included fractional milliseconds, which Spec §3.2 forbids. New `rfc3339UTC()` helper used consistently.
- **`scoring_profile` field added to every `/resolve` and `/batch` response** — per Spec REQ-5, conformant resolvers must return this field. The default profile identifier `dillclaw-default-v1` is now emitted in every response envelope, including error responses, enabling clients to verify (per REQ-6) that scores from different responses are comparable.
- **Banker's rounding for trust scores** — per Spec §6.2 (REQ-29), aggregate scores must use round-half-to-even (IEEE 754 roundTiesToEven). Earlier releases used JavaScript's `Math.round`, which rounds half away from zero and would produce non-deterministic results across conformant implementations for scores landing exactly on a half-thousandth. New `bankersRound3()` helper.
- **Deterministic tie-breaking** — per Spec §6.3 (REQ-31), when two candidates produce identical rounded scores, the ranking now applies Rule 1 (ascending lexicographic namespace path) and Rule 2 (ascending semver precedence) instead of falling back to registry-iteration order. New `compareSemver()` helper implements semver.org §11 precedence rules including pre-release identifier comparison.
- **`trace_id` in every response, including errors** — per Spec REQ-10, every response must carry a `trace_id`. Earlier releases generated the trace ID only after request validation succeeded; error responses (malformed JSON, missing fields, bad Content-Type) carried none. The trace ID is now generated at handler entry and included in every response envelope.
- **Missing-signature signal renamed `sig_unverified`** — per Spec REQ-26, candidates with missing signatures must be marked with the exact label `sig_unverified`. Earlier releases used `sig_absent`.
- **Stale-while-revalidate window cutoff enforced** — per Spec §7.3 and REQ-35, when the stale window expires the resolver must return `REGISTRY_UNAVAILABLE` rather than continuing to serve old cached data. Earlier releases had no cutoff — data could be served indefinitely after the registry became unreachable. The window is now tracked from first refresh failure and checked both during refresh cycles and at read time. Default 900s, override via `DILLCLAW_STALE_WINDOW_MS` (clamped to spec max 1800s).
- **Content-Type explicit check** — per Spec §5.2, `POST /resolve` and `POST /batch` requests must be `application/json`. Earlier releases relied on JSON parse failure to reject non-JSON bodies; the header is now checked explicitly with a clear error message.

## What's new in v0.1.6

- **Scheme-form conformance fix** — the resolver now accepts both URI scheme forms defined in Namespace Standard v0.4.2 §3.4: the full form `dillweed://` and the canonical short form `dllwd://`. The two are treated as semantically equivalent, as the specification requires. Earlier releases accepted only `dillweed://` and rejected `dllwd://` with `QUERY_MALFORMED` — a conformance defect, since the spec names `dllwd://` as the preferred form for resolver queries and API contexts. The query-syntax examples in this README and the `test.sh` suite have been updated accordingly; `test.sh` now includes explicit short-form equivalence tests.

## What's new in v0.1.5

- **License changed to Apache 2.0** — the per-service `LICENSE` file is now the Apache License 2.0, matching the project-wide licensing decision. A `NOTICE` file has been added carrying attribution and the trademark policy (Apache 2.0 §4d). The `package.json` `license` field is now `Apache-2.0`. This supersedes the MIT license that shipped with earlier reference-implementation tarballs; the change was made before any public distribution.
- **Internal version-stamp correction** — the `VERSION` constant in `server.js` (emitted as `resolver_version` in every `/resolve` response and as the `User-Agent` on registry fetches) was stale at `dillclaw/0.1.1` across several prior releases; it now tracks the package version. The depicted `resolver_version` values in this README's example responses were corrected to match. The `test.sh` header now carries a version stamp for consistency with the Registry and Anthill test suites.

## What's new in v0.1.4

- **Installer hardening: dependencies install fails visibly** — the resolver's installer previously ran `npm install --silent 2>/dev/null || true`, which suppressed all errors and continued. The installer now runs `npm install --silent` under `set -e`, so any dependency installation failure halts the installer with a clear error rather than producing a partial install that fails mysteriously later. The resolver currently has no npm dependencies, but the change matters for any future-added dependency and matches the fail-fast posture of the Registry and Anthill installers.

- **Installer hardening: secured launchd plist permissions** — the installer now calls `chmod 600` on the plist file immediately after writing it. The resolver's plist does not currently contain secrets, but the same permission discipline is applied across all three Dillweed installers for consistent hygiene.

## What's new in v0.1.3

- **Trust-root callout in README** — added an `⚠ Important: Trust Roots and Public Keys` section at the top of this README, making explicit that the resolver's behavior depends on which DNSO public key it is configured to verify against, and that operating against a local development key is not the same as operating against the canonical Dillweed Namespace.

- **Internal version-stamp corrections** — the hardcoded version strings in `server.js` (header comment, startup banner) now match the `package.json` version (v0.1.3). The earlier port-renumbering bumped `package.json` but did not propagate to these internal strings; that gap is closed.

The Resolver's existing structural-signature-fallback warning (introduced in v0.1.1 when no DNSO key is configured) continues to operate as before. No new startup behavior was added in this release.

## What's new in v0.1.2

- **Port renumbering** — the service's default port has changed from `7474` to `9474`. The `7474`-`7476` range conflicted with Neo4j's well-known ports; the `9474`-`9476` range avoids that conflict. If you set the port explicitly via the `*_PORT` environment variable in your deployment, no action is needed. If you relied on the default port, you must update your client configuration to use the new port.

## Enable real Ed25519 signature verification

**The bundled tarball ships with a sample DNSO public key (`dnso_public.pem`) and a `registry.json` whose 6 non-prerelease records are signed by the matching sample private key.** This makes out-of-the-box signature verification work without any setup — the resolver starts, loads the bundled public key, and validates the bundled sample records. The sample private key is not shipped; only the public verifier is.

If you want to issue your own DNSO key and re-sign the sample registry under your own trust root, generate a fresh keypair:

```bash
node tools/generate-keys.js
# or, equivalently:
npm run generate-keys
```

This creates three things in the resolver directory:

- `dnso_private.pem` — the DNSO signing key (keep secret)
- `dnso_public.pem`  — the verification key the resolver loads on startup
- `registry.json`    — updated in place with real Ed25519 signatures

Records with `signature: null` are intentionally left unsigned — they exist to exercise the resolver's `allow_unsigned` request policy. The bundled `tools.search.web-retrieval@4.0.0-beta` record is one such test fixture.

Restart the resolver. The startup banner will say `DNSO key  configured (dnso_public.pem, ed25519)` and every resolution will perform real cryptographic verification using the canonical JSON format that matches the Registry v0.1.4 / v0.2.7 signing profile (top-level fields only, base64url-encoded Ed25519, IEEE P1363).

> **Security note.** The bundled sample keypair is for development and demonstration only. **It is not a real DNSO trust root.** In a production DNSO deployment, the signing key lives in an HSM or equivalent. This reference implementation uses a local PEM file because its purpose is to demonstrate the protocol contract end-to-end, not to replace the operational DNSO.

## Fetch records from a live Registry

Set `DILLCLAW_REGISTRY_BASE_URL` to the base URL of a running Registry:

```bash
export DILLCLAW_REGISTRY_BASE_URL=http://localhost:9475
./start.sh
```

The resolver integrates with the Registry via its standard endpoints:

- **Startup and periodic refresh:** `GET <base>/list` warms the in-memory snapshot. Refresh interval is `DILLCLAW_REGISTRY_REFRESH_MS` (default 60s).
- **Cache miss for exact name:** `GET <base>/lookup/<name>` retrieves a single record when the query asks for a specific capability that isn't in the warm snapshot. Wildcard and fuzzy queries are served from the snapshot only.
- **Stale-while-revalidate (spec §7.3):** if `/list` refresh fails while a snapshot is available, the snapshot is served as stale for up to `DILLCLAW_STALE_WINDOW_MS` (default 900s, max 1800s). After the window expires, `/resolve` returns `REGISTRY_UNAVAILABLE` rather than continuing to serve stale data.

The legacy `DILLCLAW_REGISTRY_URL` variable is still accepted as an alias for `DILLCLAW_REGISTRY_BASE_URL` for backward compatibility — but the value should be the **base URL** (e.g. `http://localhost:9475`), not a `/list` or `/capabilities` path. If both are set, `DILLCLAW_REGISTRY_BASE_URL` takes precedence.

## Starting the Resolver (full options)

```bash
# Default port
./start.sh

# Custom port
DILLCLAW_PORT=8080 ./start.sh

# Remote Registry with 30-second refresh
DILLCLAW_REGISTRY_BASE_URL=http://localhost:9475 \
DILLCLAW_REGISTRY_REFRESH_MS=30000 \
./start.sh

# Custom DNSO public key path
DILLCLAW_DNSO_PUBLIC_KEY=/etc/dillweed/dnso_public.pem ./start.sh
```

Or start directly with Node:

```bash
node server.js
```

## API Reference

### `POST /resolve` — Resolve a capability

The primary endpoint. All fields except `query` are optional.

```bash
curl -s -X POST http://localhost:9474/resolve \
  -H "Content-Type: application/json" \
  -d '{
    "query": "dllwd://research.market.intel.vendors",
    "trust_minimum": "verified",
    "permissions": ["query", "export"],
    "version_pref": "stable",
    "max_results": 1,
    "context": { "caller_id": "agent-42", "session_id": "s-abc" }
  }' | jq .
```

**Request fields:**

| Field | Type | Default | Description |
|---|---|---|---|
| `query` | string | required | Dillweed namespace URI |
| `trust_minimum` | string | `"experimental"` | Minimum trust tier: `experimental`, `trusted`, `verified`, `canonical` |
| `permissions` | array | `[]` | Required permissions the capability must carry |
| `version_pref` | string | `"stable"` | `"stable"` (filter out prereleases), `"latest"` (no filter), or semver string |
| `max_results` | integer | `1` | Maximum candidates to return (ranked by trust score) |
| `context` | object | `{}` | Optional `{ caller_id, session_id }` retained in the trace record |

**Response fields (when `status === "resolved"`):**

```json
{
  "status": "resolved",
  "results": [{
    "rank": 1,
    "capability": { ... full capability record ... },
    "trust_score": 0.914,
    "trust_signals": ["dnso_verified", "19mo_history", "sig_valid", "sig_verified", "endpoint_unchecked"],
    "cache_hit": false
  }],
  "query":            "dllwd://research.market.intel.vendors",
  "resolved_at":      "2026-04-18T15:04:32Z",
  "trace_id":         "trc_9f2a1b3c4d5e6f7a",
  "resolver_version": "dillclaw/0.1.7",
  "scoring_profile":  "dillclaw-default-v1"
}
```

When the registry is serving cached data after a failed refresh, the response envelope also includes:

```json
{
  "stale":     true,
  "cached_at": "2026-04-18T14:59:12Z"
}
```

`trust_signals` includes `sig_verified` only when the signature passed cryptographic verification against the configured DNSO public key. `sig_valid` is present for any non-`INVALID` signature (present and well-formed); `sig_unverified` for records without signatures (per Spec §6.1 REQ-26); `sig_invalid` for verification failures or malformed signatures.

### `GET /trace/<trace_id>` — Audit trace

Every resolution response includes a `trace_id`. Retrieve the full resolution trace:

```bash
curl -s http://localhost:9474/trace/trc_9f2a1b3c4d5e6f7a | jq .
```

Traces now include `caller_id` and `session_id` from the request's `context` field when present. Traces are stored in `./traces/` and retained until manually cleared.

### `POST /batch` — Batch resolution

Resolve up to 50 queries in a single call:

```bash
curl -s -X POST http://localhost:9474/batch \
  -H "Content-Type: application/json" \
  -d '{
    "requests": [
      {"query": "dllwd://research.market.intel.vendors"},
      {"query": "dllwd://data.enrichment.company.profile", "trust_minimum": "verified"}
    ]
  }' | jq .
```

## Query Syntax

Queries use the canonical short form `dllwd://`. The full form `dillweed://` is
also accepted and treated as semantically equivalent (Namespace Standard §3.4).

| Pattern | Meaning |
|---|---|
| `dllwd://research.market.intel.vendors` | Exact match |
| `dllwd://research.market.*.vendors` | Wildcard: any subcategory |
| `dllwd://tools.search.*` | Wildcard: any tool under search |
| `dllwd://tools.search.web-retrieval:1.2.0` | Exact version |
| `dllwd://tools.search.web-retrieval:^1.2` | Caret range: >=1.2, <2.0 |

**Rules:** paths must be lowercase, hyphens allowed, no underscores. First component cannot be a wildcard. Maximum two wildcards per query.

## Trust Tiers

| Tier | Meaning |
|---|---|
| `canonical` | DNSO-designated preferred implementation |
| `verified` | Identity confirmed, endpoint tested, DNSO review complete |
| `trusted` | Proven usage history, elevated from community standing |
| `experimental` | Early stage or limited validation |

### Trust Score Formula

```
score = (tier_score × 0.40) + (usage_history × 0.30) + (sig_validity × 0.20) + (liveness × 0.10)
```

Where `sig_validity` is 1.0 for a cryptographically verified signature, 0.5 for a present-but-unverified (or absent) signature, and 0.0 for a failed verification or explicit `"INVALID"`.
